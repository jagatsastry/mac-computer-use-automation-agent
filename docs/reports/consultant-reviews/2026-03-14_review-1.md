# External Consultant Review #1: Cross-Suite Customer Testing Analysis

**Date**: 2026-03-14
**Reviewer**: External Consultant (via codex exec)
**Scope**: All 4 customer testing suites (Target buy bedsheets, Amazon return, Walmart return, Survey gaps) — 45 total runs across 12 cycles

---

## Consultant Assessment

Project health is mixed: infrastructure health is good, product health is poor. As of the March 14, 2026 reports, the team has clearly stabilized screenshots, verification, retries, and observability, but the browser interaction layer is still asking a screenshot-grounding model to solve problems that should be handled structurally. At 4/16 scenario passes overall, this is still a research prototype, not a useful customer automation agent.

The strongest signal in the data is architectural, not model-tuning-related: every time you replace fine-grained UI interaction with deterministic navigation, reliability jumps. The repo already shows that pattern unevenly: Target is now URL-first in buy_on_target.md, while Amazon remains underspecified in return_amazon_order.md. Safety classification is currently keyword-based in agent.py, and the hybrid grounding stack already exists but important features are default-off in config.py, agent.py, and coordinator.py.

## Consultant Answers to Questions

### Q1: URL-first, vision-fallback strategy?
**Answer**: Yes — shift to `URL-first, structure-second, vision-last`. For browser tasks, navigation is a state-transition problem, not a perception problem. Trade-off: you lose some generality and take on per-site maintenance, but you gain far more reliability, speed, and safety.

### Q2: Grounding model investment priority?
**Answer**: Do NOT make "find a better grounding model" the main bet. Priority:
1. DOM/accessibility/browser-query hybrid
2. Turn on and benchmark the hybrid features already built (dual-res, SOM — currently default-off)
3. Dual-resolution/cropped grounding for dense local regions
4. Only then run limited model bake-offs on exact sites

### Q3: type_text fix approach?
**Answer**: The right answer is `b + c + d`, with `a` as fallback. For browser pages, prefer direct field focus/value-setting through DOM or browser-side JS, with proper input/change events. If unavailable, click-to-focus, then verify focus before typing.

### Q4: Confidence threshold for "Purchase History" vs "Purchase this item"?
**Answer**: Short term — add safe-navigation exemptions for "Purchase History", "Order History", "View order details". Long term — classify by action intent + page state (navigation, selection, form-fill, destructive commit as different classes).

### Q5: Minimum viable pass rate?
**Answer**: 70% clean-state for useful-with-supervision, 85%+ for customer pilot. More important: wrong-item or wrong-page actions must be near zero. Critical path:
1. Deterministic navigation to the right page
2. Deterministic form/link interaction in browsers
3. Replans that preserve the remaining task graph

### Q6: Fundamental architectural changes?
**Answer**: Split architecture by surface:
1. Browser tasks: browser-aware adapter layer (URLs, DOM/accessibility queries, page contracts, JS helpers)
2. Native desktop tasks: keep vision + AX + pyautogui
3. Vision: use for verification, recovery, and unsupported surfaces — NOT the primary control plane for common web flows

---

## Top 3 Highest-Impact Changes

1. **Build a browser interaction layer for supported sites.** Deep links, page-type checks, order-page vs product-page validation, disabled-state detection, and field setting should be structural, not visual.

2. **Strengthen skills into site adapters.** Amazon especially is too shallow today compared with Walmart and Target; that forces the planner to improvise on the hardest steps.

3. **Replace keyword safety and local replans with typed action/page contracts.** The current one-step tactical replan behavior is exactly why strategic context gets dropped, even though the prompt already says navigation steps are a contract.

---

## Methodology Patterns and Risks

### Good Patterns
- Testing in cycles, capturing screenshots, isolating concrete failure modes — strong engineering discipline

### Anti-Patterns
- **Too much effort retrying around grounding weakness** instead of removing the need for grounding
- **Scenario contamination masking reality** — some "passes" inherited browser state or stopped at an intermediate page

### Blind Spots
- Promising hybrid features already implemented but still disabled/unvalidated in customer tests (SOM, dual-res, lookahead)

### Risks
- **Unsafe "success"**: A wrong item, wrong order, or wrong page that looks plausible is far more damaging than a clean failure
- **Overfitting to URL hacks without declaring a supported-surface strategy** — fine if intentionally becoming a site-adapter system; problematic if marketing as broadly general browser automation
