# Codebase Concerns

**Analysis Date:** 2026-03-20

## Tech Debt

**Broad exception handling throughout orchestrator:**
- Issue: 40+ instances of `except Exception:` silently catching and logging all errors across verifier, grounding, context monitor, and main agent
- Files: `src/automation_agent/orchestrator/agent.py` (20+ occurrences), `src/automation_agent/orchestrator/verifier.py` (6 occurrences), `src/automation_agent/orchestrator/grounding_router.py` (5 occurrences), `src/automation_agent/orchestrator/context_monitor.py` (2 occurrences)
- Impact: Makes debugging difficult; masks different failure modes (network errors, timeouts, logic bugs) with identical logging; error recovery strategies can't be tailored
- Fix approach: Replace generic `except Exception:` with specific exception types. Create exception hierarchy for distinguishing transient failures (network, timeout) from permanent ones (logic, config). Add structured error context for debugging.

**Large monolithic agent orchestrator:**
- Issue: `src/automation_agent/orchestrator/agent.py` is 5449 lines with 100+ methods, mixing execution control, verification logic, error recovery, skill learning, and state management
- Files: `src/automation_agent/orchestrator/agent.py` (lines 1-5450)
- Impact: Cognitive load for maintenance; method interdependencies are implicit; refactoring requires understanding entire file; testing requires extensive mocking
- Fix approach: Extract distinct responsibilities into separate classes: `StepExecutor` (action invocation + lookahead), `StateTracker` (screenshot diffs, pixel changes), `RecoveryCoordinator` (replan logic + frustration scoring), `SkillLearningCoordinator` (observation extraction + promotion). Keep `AutomationAgent` as thin orchestrator. This is incremental — don't do all at once.

**Unchecked coordinate space assumptions in vision models:**
- Issue: `src/automation_agent/vision/coordinator.py` defines COORDINATE_SPACES registry (lines 25-35). Unknown models raise ValueError, but legacy code may have hardcoded assumptions. GPT grounding had an offset bug fixed in prior commit.
- Files: `src/automation_agent/vision/coordinator.py` (COORDINATE_SPACES mapping), `src/automation_agent/orchestrator/grounding_router.py` (_ground_accessibility_match uses confidence calibration)
- Impact: New vision models added without coordinate space entry cause runtime crash. Offset bugs recur if new coordinate conversions added without proper testing.
- Fix approach: Add coordinate space validation to model registration (fail at config load). Create `@dataclass CoordinateSpace(name, scale_factor, validation_fn)` to centralize conversions. Add benchmark test for each new model before shipping.

**Loose precondition/verify field chaining:**
- Issue: Preconditions are optional and generated by planner. No validation that step N's verify matches step N+1's precondition. Broken chains cause silent failures during verification.
- Files: `src/automation_agent/shared_models.py` (ActionStep definition, lines 1-400), `src/automation_agent/planner/planner.py` (precondition generation logic)
- Impact: If planner generates "assert window has search box" in step 2 but step 1 verify is "page loaded" (not specific about search box), step 2's precondition fails silently
- Fix approach: Add post-plan validation in `_validate_plan()` to check precondition→verify chains are compatible. Use embeddings to check semantic similarity (cosine > 0.7) for preconditions that don't exactly match prior verify.

**Safari JavaScript prerequisite not validated at setup:**
- Issue: Safari requires "Allow JavaScript from Apple Events" to be manually enabled. Currently detected at runtime via stderr parsing (line 462 in applescript_actuator.py) and logged once, then disabled for session.
- Files: `src/automation_agent/actuator/applescript_actuator.py` (lines 460-470), `src/automation_agent/config.py`
- Impact: User doesn't discover this until first Safari JS call (could be 20 steps into an automation). No early warning during `--dry-run` or agent init. Silent disabling of JS verification breaks assumptions downstream.
- Fix approach: Add `validate_safari_js()` as part of config validation (in AgentConfig.__init__ or _call_validate hooks). Call early during agent init. If disabled, warn prominently in logs + require opt-in via `AGENT_ALLOW_DEGRADED_SAFARI=true` env var.

**Temporary file cleanup not guaranteed:**
- Issue: `_atomic_write()` in `src/automation_agent/skills/librarian.py` (lines 47-52) uses `path.with_suffix(path.suffix + ".tmp")` but relies on `os.replace()` succeeding. If it fails partway, .tmp files accumulate. No cleanup on agent exit.
- Files: `src/automation_agent/skills/librarian.py` (lines 50-52), `src/automation_agent/skills/experience.py` (lines 132-134)
- Impact: Disk space leak if writes fail during skill learning; stale .tmp files prevent re-runs from cleaning up old observations
- Fix approach: Use `tempfile.NamedTemporaryFile(delete=False)` in a context manager. On success, move to target. On failure, delete temp file explicitly. Add cleanup hook to agent exit handler.

## Known Bugs

**Molmo2 vision output format quirk:**
- Symptoms: Molmo2 sometimes outputs `FOUND: x=851 090` instead of `FOUND: x=851 y=090` (missing `y=` label)
- Files: `src/automation_agent/vision/coordinator.py` (_parse_coordinates method has regex fallback)
- Trigger: Inconsistent Molmo2 output format; the regex fallback handles it: `FOUND:\s*x\s*=\s*([0-9.]+)\s+([0-9.]+)` (groups x as group 1, y as group 2)
- Workaround: In place — uses the fallback regex pattern. No action needed but document the quirk in COORDINATE_SPACES comments.

**mlx-vlm float16 overflow in Molmo2:**
- Symptoms: Molmo2 crashes with "tensor value out of range" when vision activations exceed float16 max (~65504)
- Files: `.venv-molmo2/lib/python3.11/site-packages/mlx_vlm/models/molmo2/` (two patches applied)
  - `vision.py` line 228: Add batch dim for 3D input
  - `molmo2.py` get_input_embeddings: Use bfloat16 instead of float16
- Trigger: Large screenshots or high-saturation images; happens during embedding projection
- Workaround: Patches are applied in `.venv-molmo2` — documented in CLAUDE.md under "Molmo2 Vision Fix"

**JS verification leaks Safari focus in older macOS:**
- Symptoms: AppleScript JS execution can steal focus on some macOS versions
- Files: `src/automation_agent/actuator/applescript_actuator.py` (_get_browser_js_batch method, lines 400-470)
- Trigger: Running with `AGENT_JS_VERIFICATION_ENABLED=true` on macOS 12.x or earlier
- Workaround: `_try_enable_safari_js()` was removed in prior commit to avoid focus-stealing dialogs. JS verification uses per-session blocklist instead. No cross-app focus shift observed in current implementation (uses direct AppleScript, not open dialog).

## Security Considerations

**API key handling in config:**
- Risk: AGENT_ANTHROPIC_API_KEY, AGENT_GEMINI_API_KEY, AGENT_OPENAI_API_KEY loaded from environment variables prefixed AGENT_
- Files: `src/automation_agent/config.py` (lines 108-200), field validators strip whitespace but don't mask on repr
- Current mitigation: Pydantic Settings loads from .env which is .gitignored; env vars are not logged except in debug mode
- Recommendations:
  1. Add `@model_validator` that masks API key repr (return `***REDACTED***` in __repr__)
  2. Add config validation to warn if API keys set but model provider not configured to use them (avoid accidental leaks to logs)
  3. Document that .env must not be committed; consider auto-checking in CI

**Vision server URL not validated:**
- Risk: AGENT_VISION_SERVER_URL defaults to localhost:8080 but accepts any URL; no TLS validation for HTTPS; credentials not supported
- Files: `src/automation_agent/config.py` (vision_server_url field, line 72)
- Current mitigation: Default is localhost; used only for local development
- Recommendations:
  1. Validate URL format on config load; disallow http:// in production (detect via env or env_name)
  2. Add optional vision_server_auth_token if using remote server (passed as Bearer token)
  3. Warn if vision server is not localhost and TLS is not enforced

**Skill observation data not sanitized:**
- Risk: Skill observations may contain user input (alternative_path, checkpoint labels) extracted from execution traces. No HTML escaping or injection prevention.
- Files: `src/automation_agent/skills/distiller.py` (observation extraction), `src/automation_agent/skills/experience.py` (persistence)
- Current mitigation: Observations are stored as JSONL, not rendered in UI; footprint is local disk only
- Recommendations:
  1. Add optional sanitization step when loading observations for planner context
  2. If observations are ever exposed in UI or web API, apply context-aware escaping (HTML for web, shell-safe for logs)

## Performance Bottlenecks

**Vision verification tier 2 (screenshot) latency:**
- Problem: StepVerifier.verify() falls through to Tier 2 (vision verification) on failed Tier 0/1 checks; each screenshot verification takes 2-5s
- Files: `src/automation_agent/orchestrator/verifier.py` (lines 160-200), `src/automation_agent/orchestrator/agent.py` (lines 2200+)
- Cause: No caching of screenshot descriptions; each verify call re-encodes screenshot to base64 and re-calls vision model
- Improvement path:
  1. Cache screenshot hash → description for 1s (prevents re-calls on rapid retries)
  2. Batch verify calls when multiple steps fail (verify 3 steps' conditions on single screenshot, not 3 separate calls)
  3. Use confidence thresholding: if Tier 1 confidence >= 0.8, skip Tier 2

**Librarian observation grouping is O(n²):**
- Problem: `_group_observations()` in `src/automation_agent/skills/librarian.py` (line ~250) deduplicates by normalizing keys, then checks each observation against all seen keys
- Files: `src/automation_agent/skills/librarian.py` (lines 240-270)
- Cause: For 100+ observations per skill, this becomes slow; scales quadratically
- Improvement path:
  1. Use dict with normalized key for O(1) dedup: `seen[_normalize_key(obs.category, obs.recommendation)] = obs`
  2. Add observation cap: limit to 500 per skill file (append-only JSONL grows unbounded)
  3. Periodically prune observations older than 30 days

**Skill experience store loads entire JSONL into memory:**
- Problem: `SkillExperienceStore.load()` reads entire file and parses all lines even if only needing top 5
- Files: `src/automation_agent/skills/experience.py` (lines 38-58)
- Cause: No pagination; skill files can grow to 10K+ observations
- Improvement path:
  1. Add `load(limit=None, since_timestamp=None)` parameters
  2. Read file in reverse order (tail -n) to get most recent observations first
  3. Cache loaded observations in memory with TTL (5 min)

**AppleScript accessibility bridge query timeout (3s):**
- Problem: `get_accessibility_elements()` in `src/automation_agent/actuator/applescript_actuator.py` (line 330) times out after 3s, blocking verification
- Files: `src/automation_agent/actuator/applescript_actuator.py` (lines 330-360)
- Cause: JXA window tree traversal can be slow on apps with complex DOM (web browsers with many iframes)
- Improvement path:
  1. Cache accessibility snapshot for 500ms (most pages don't change that fast)
  2. Add element count limit: return first 100 elements found, not all
  3. Implement progressive depth limit (traverse only 3 levels deep first, then expand if needed)

## Fragile Areas

**Replan loop with same-state detection:**
- Files: `src/automation_agent/orchestrator/agent.py` (FrustrationScore, lines 800-900; _execute_replan, lines 4600+)
- Why fragile: Same-state detection counts identical screenshots. If UI is animating (e.g., loading spinner), every screenshot differs slightly, breaking same-state detection. Replan loop could run unnecessarily.
- Safe modification: Diff screenshots with tolerance (ignore regions with high motion, like spinners). Add optional spinner detection via accessibility.
- Test coverage: `tests/unit/test_plan_robustness.py` covers replan basics, but no tests for animated UIs or edge cases

**Precondition verification chain:**
- Files: `src/automation_agent/orchestrator/agent.py` (lines 1560-1610), `src/automation_agent/orchestrator/verifier.py` (lines 49-150)
- Why fragile: Preconditions are checked before action, but if verification itself is flaky (vision model inconsistent), precondition checks fail and replan is triggered. This creates a cascade.
- Safe modification: When precondition fails, first retry precondition check with fresh screenshot before replanning. Log precondition failures separately so root causes are visible.
- Test coverage: No dedicated test suite for precondition chains. Covered implicitly in integration tests.

**Lookahead prediction for destructive steps:**
- Files: `src/automation_agent/orchestrator/agent.py` (lines 1650-1780), coordinator.predict_action_outcome()
- Why fragile: Lookahead is optional (gated by CoordinatorCapability.LOOKAHEAD). If coordinator doesn't implement it, silently skipped. Planner may assume lookahead ran, causing destructive action to proceed without safety check.
- Safe modification: Store `lookahead_performed` flag in StepResult. If destructive step has no lookahead and no confirmation was shown, log warning.
- Test coverage: `tests/unit/test_lookahead.py` has 30+ tests, but assumes coordinator has lookahead capability.

**Skill matching with embedding fallback:**
- Files: `src/automation_agent/skills/router.py` (lines 100-180), `src/automation_agent/skills/registry.py` (match method)
- Why fragile: Three-stage matching (direct → embedding → keyword) means if embedding model is unavailable, falls back to keyword matching silently. Keyword matching is less accurate.
- Safe modification: Log when fallback occurs with specific reason (embedding disabled, model unavailable). Store which strategy matched in SkillMatchResult for observability.
- Test coverage: `tests/unit/test_skill_registry.py` has fallback tests, but no explicit coverage for embedding unavailability

**AppleScript string escaping for special characters:**
- Files: `src/automation_agent/actuator/applescript_actuator.py` (_escape_for_applescript, lines 365-375)
- Why fragile: Escaping only handles newline, CR, tab. Other special chars (quotes, backslashes) may not be escaped correctly. Unicode directional overrides could break output parsing.
- Safe modification: Add comprehensive escaping for all metacharacters. Use AppleScript's `«class utxt»` syntax for binary-safe string passing if available.
- Test coverage: No dedicated tests for escaping edge cases. `tests/unit/test_applescript_actuator.py` has basic tests.

## Scaling Limits

**Skill library unbounded growth:**
- Current capacity: JSONL experience files have no size limit; librarian can append 1000s of observations
- Limit: At 10K observations/skill, loading and deduplication becomes slow (O(n²) grouping); disk I/O dominates
- Scaling path:
  1. Implement observation expiry (delete older than 30 days)
  2. Archive observations to separate "learned_tips" section once promoted
  3. Implement pagination for experience loading (load in chunks, not all at once)

**Screenshot diff tracking memory:**
- Current capacity: ScreenshotDiff keeps hash of current + prior screenshot in memory; caches up to 10 screenshots
- Limit: On long automation runs (100+ steps), screenshot cache can grow to 200MB+ if screenshots are large (4K resolution)
- Scaling path:
  1. Use disk-based LRU cache for large screenshots (keep only last 3 in memory)
  2. Compress cached screenshots with lossy JPEG compression
  3. Add max cache size config (default 500MB)

**Replan history per execution:**
- Current capacity: ExecutionResult.replans list grows with each replan; no limit
- Limit: On highly adversarial tasks with 10+ replans, replan history can reach 50KB+ of JSON
- Scaling path:
  1. Cap replans list to 5 most recent (older ones less relevant for learning)
  2. Compress old replan entries (store only deltas, not full steps)

**Context monitor world-state document:**
- Current capacity: ContextMonitor accumulates milestones + obstacles; no pruning
- Limit: After 100+ steps, world-state document grows to 10K+ tokens; wastes LLM context
- Scaling path:
  1. Keep only last 20 milestones/obstacles in active context
  2. Summarize older ones into checkpoint summary
  3. Prune obstacles after they're resolved (if precondition checks pass)

## Dependencies at Risk

**PyAutoGUI + PyInput for keyboard/mouse:**
- Risk: Both are macOS-specific; PyAutoGUI has stalled development (last release 0.9.54 in Dec 2023); pynput is more active but adds another input library
- Impact: If PyAutoGUI breaks on future macOS versions, no maintained alternative readily available
- Migration plan: Consider standardizing on pynput for all input (it supports mouse + keyboard); migrate PyAutoGUI keyboard calls to pynput equivalents

**Ollama SDK version pinning:**
- Risk: `ollama>=0.1.6` has no upper bound; breaking changes in ollama 1.x+ could break local vision server integration
- Impact: pip install without constraints may pull incompatible versions
- Migration plan: Pin to `ollama>=0.1.6,<1.0` in pyproject.toml; test against latest ollama version monthly

**Pydantic v2 dependency:**
- Risk: Major version bump; any migration to v3 would require significant config refactoring
- Impact: Long-term lock-in to Pydantic v2; can't easily switch to alternative validation library
- Migration plan: Document which Pydantic v2 features are critical (Settings, validators, field_validator); plan v3 migration path if needed

**mlx-vlm for local Molmo:**
- Risk: MLX is Apple-only (requires M1+); mlx-vlm's molmo2 support is experimental (uses patches for bfloat16 overflow)
- Impact: Can't easily replace Molmo if mlx-vlm becomes abandoned; no ARM-compatible alternative with same accuracy
- Migration plan: Monitor ONNX support for Molmo; prepare fallback to DistilBERT-based grounding if mlx-vlm breaks

## Missing Critical Features

**No cross-device session persistence:**
- Problem: Each run is isolated; agent can't save state and resume on another device or after restart
- Blocks: Multi-hour automations that timeout; error recovery across reboots; distributed agent scenarios
- Gap: No serialization of execution state beyond run logs; no resume checkpoint mechanism

**No explicit error categorization for learning:**
- Problem: Observations mark "error" as string, but no structured error type (e.g., network vs. logic vs. UI change)
- Blocks: Skill promotion can't distinguish "this approach failed because UI changed" from "this approach is broken"; learning becomes noisy
- Gap: SkillObservation.error is untyped string; should be Enum(NETWORK, UI_CHANGED, LOGIC_ERROR, TIMEOUT, etc.)

**No confidence scoring for plans:**
- Problem: Planner generates ActionPlan but doesn't score its own confidence; no signal for "this is risky, consider getting user confirmation"
- Blocks: Adaptive confirmation (currently binary always/smart/never, should be confidence-based)
- Gap: ActionPlan lacks confidence field; planner doesn't self-evaluate
